# RFC: 显式语义检索与可解释候选融合

- **ID**: 0019
- **状态**: Accepted
- **作者**: @ld
- **起草日期**: 2026-08-27
- **关联**: RFC 0016、RFC 0018

## 摘要

默认检索只使用 FTS5/LIKE。只有显式配置真实 embedding provider 时，系统才加入独立语义候选。文本与语义通道通过排名融合，再结合文档结构特征重排；低相似度候选被过滤，文档范围在向量 top-k 之前生效。

## 动机

原默认 `HashEncoder` 只是词项哈希，却被作为 semantic 通道使用。它会增加构建和存储成本，无法可靠处理同义改写，还可能因哈希碰撞召回无关内容。原排序直接把手工文本分数和余弦分数相加，不同通道的分值没有统一尺度；向量索引也只检查“是否存在”，中断后留下的部分索引无法自动补齐。

检索层需要保证的是候选来源透明、范围正确、失败可降级和派生索引可恢复，而不是假定任意向量都代表语义。

## 详细设计

### 默认与降级

- `embeddings.provider` 默认是 `none`，L1 继续使用 FTS5/LIKE。
- `bge_m3`、`openai` 和 `openai_compat` 提供独立语义候选。
- `hash` 保留给测试和显式的离线链路验证，但不作为独立语义召回通道。
- 运行时只打开状态成功、配置指纹一致且 node/chunk 内容 hash 完整匹配的向量索引。provider 缺失依赖、凭证或查询失败时降级为文本检索，通过查询 `warnings` 说明原因，不静默换用另一种 encoder。

### 候选与排序

```text
完整 task 的文本命中
  + task 关键词的文本命中
  + 文档范围内、超过最低相似度的语义命中
  → 去重
  → RRF 融合各通道排名
  → 标题、章节、正文词项、表头、caption 和 chunk 类型重排
```

FTS 候选在数据库截断前按 BM25 排序；LIKE 仅在 CJK 或 FTS 候选不足时补位。RRF 只比较通道内排名，避免把 FTS、启发式分数和不同 embedding 模型的原始分数直接等量相加。余弦相似度在向量后端之间保持同一语义；语义候选必须先应用 `doc_ids` 和实体类型范围。

### 索引恢复

构建时按当前 provider/model 比较完整的 node/chunk ID 与内容 hash。缺项、陈旧项、模型切换或部分写入都会触发增量补齐；向量仍是可重建派生数据，不改变 L0/L1 schema。

检索分页冻结首轮候选 ID、分数和排序原因，并在游标中恢复 task 与 `doc_ids`。续页不重新编码查询；L1 快照变化后游标失效。

## 备选方案

### 保留默认 hash 向量

不采用。它与 FTS/LIKE 提供的信息高度重合，却容易被用户理解成真正的语义能力。

### 直接线性相加 BM25 和余弦分数

不采用。不同后端、模型和查询下的分数分布不同，需要额外校准；排名融合更稳定，也不增加项目级配置。

### 为每个 provider 暴露阈值和权重

暂不采用。当前规模下统一保守默认值足够，增加配置会把执行策略转嫁给使用者。后续应先用版本化评测集校准，再决定是否开放参数。

## 迁移路径

- 用户和项目配置都未写 `embeddings` 时使用纯文本检索，不再读取旧 hash 向量。
- 已有用户级配置若写了 `provider: hash`，它仍是显式偏好；改为 `none` 才会关闭。
- 需要语义召回的项目显式配置 `bge_m3` 或 OpenAI-compatible provider，并重新运行 `docgraph build`。
- 无数据库 migration；旧向量是派生数据，可保留到下次清理或被新模型覆盖。
- 项目处于开发阶段，不保留旧默认行为的兼容开关。

## 验证

- 覆盖中文任务的词项探测、hash 碰撞不进入语义召回、低分过滤和文档范围。
- 覆盖部分向量索引检测及自动补齐。
- 对 SQLite JSON 和 LanceDB 使用统一余弦分数语义。
- MCP 继续通过 `retrieval_methods` 和 `rank_reasons` 暴露实际执行路径。
